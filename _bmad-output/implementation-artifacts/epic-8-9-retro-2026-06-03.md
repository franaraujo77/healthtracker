## 1. Epic Summary

**Epic 8 — Operator can manage extraction quality.** Introduced the **operator** as the *third RLS principal* (after patient and doctor): internal staff who triage the anonymised manual review queue. 8.1 shipped the read surface (`operatorProcedure` gated on the `OPERATOR_USER_IDS` env allowlist; anonymisation enforced by **RLS-policy absence** — the operator has zero policy on `users`/`uploads`, so reads zero rows; `lab_name` denormalised onto `extraction_review_queue` so no PII-bearing `uploads` join is ever needed). 8.2 shipped the write surface (confirm/reject via an in-transaction `SET LOCAL ROLE postgres` escalation rather than a new write policy; null-LOINC `operator_confirmed` observations; the `manual_entry_required` notification). 8.3 consolidated every net-new Epic 8 object into `supabase/migrations/0010_epic_8_operator_review.sql`.

**Epic 9 — Real AWS Textract extraction backend.** Replaced the `NOT_IMPLEMENTED` stub with a production Textract integration. 9.1 implemented `awsTextractAdapter.extract()` (`AnalyzeDocument` FORMS+TABLES) delegating to a **pure** `mapAnalyzeDocumentResponse`; added `@aws-sdk/client-textract`. 9.2 added a fail-loud boot gate (region pinned to `sa-east-1`, DPA-signed-credential presence; NFR-S6/S8, LGPD Art. 33). 9.3 hardened the consumer `extract()` failure path (permanent faults dead-letter; transient/programmer errors re-throw). 9.4 added a one-shot, dry-run-default stub-era re-enqueue script.

The headline payoff: a **third RLS principal** that composes cleanly with the existing patient/doctor model (anonymisation-by-absence is a genuinely new defensive pattern), and the project's **first real external-AI integration** (Textract) built entirely behind a pure/unit-testable seam so NFR-S8 (no live AWS in CI) holds.

## 3. What Went Well — concrete examples

### The 3-layer adversarial review caught a real HIGH bug on *every* Epic 9 story
This is the headline win. Brand-new surface (no prior AWS art in the repo) meant the Acceptance Auditor passing all ACs was *not* sufficient — the Blind/Edge-Case Hunters found a genuine HIGH on each:
- **9.1:** the adapter never populated `collectedAtText`, so `dispatch.ts`'s `structurallyBad` check would quarantine *every* extracted field to the review queue — the adapter as first written **could not publish a single observation**. The AC text didn't catch it; the data-flow analysis did.
- **9.2:** web-identity credentials accepted without `AWS_ROLE_ARN` (the SDK can't actually resolve that) + `AWS_REGION=""` crashing boot instead of defaulting.
- **9.3:** `LimitExceededException` (a real Textract throttle in AWS's own `THROTTLING_ERROR_CODES`) misclassified as *permanent* → would dead-letter retryable uploads. The reviewer read the installed `@aws-sdk` + `@smithy/core` source to find it.
- **9.4:** `= ANY(${reasons})` missing the `::text[]` cast every other repo call site uses (would error at runtime), plus a flip-then-send window that could strand uploads in `queued`.

The reviewers doing **real installed-SDK source research** (LimitExceededException, pg-boss `COALESCE` policy inheritance) was decisive — these aren't findable from the diff alone.

### "Pure core + thin shell" became the dominant, repeatable pattern
Every Epic 9 story extracted its non-trivial logic into a pure, unit-tested module and kept the side-effecting shell thin: `aws-mapping.ts` (block-graph traversal), `aws-config.ts` (boot gate), `aws-errors.ts` (error classifier), `reenqueue-stub-era.helpers.ts` (planner). This is **what made NFR-S8 testable** — no live AWS or DB in CI, yet the logic is covered field-by-field against recorded fixtures / fake env objects. It mirrors 9.1's own `aws-mapping` split and is now the established idiom for any external integration.

### Scope-fence discipline held across a tightly-coupled 4-story chain
9.1→9.4 are sequential dependencies (adapter → boot gate → failure path → re-enqueue). Each spec opened with an explicit **SCOPE FENCE** comment naming what it did *not* do and which later story owned it ("9.2 adds the boot gate"; "9.3 wraps the call site"). This prevented scope creep and made each story independently reviewable despite the coupling — and each story's "deferred seam" was literally the next story's opening context.

### Operator anonymisation-by-RLS-absence is a clean new security pattern
Epic 8's core defensive idea — the operator reads zero rows of `users`/`uploads` because *no policy exists*, not because of an app-layer column list — is verifiable and was locked by the operator RLS matrix. The `lab_name` denormalisation (so no PII-bearing `uploads` join) is the right structural answer to "show context without exposing identity." Operator writes escalating to `postgres` role (rather than a write policy) reused the `activateProfessionalAccount` precedent cleanly.

### Stacked-stories-on-one-PR scaled again — now across an epic boundary
PR #75 carried **8 stories across two epics**. Per-story `feat`/`fix` commit pairs + per-story review records kept it walkable. The pattern that worked for Epic 6 (5 stories) held at 8.

## 4. What Hurt — recurring patterns

### Integration-test infra is STILL dead — and this time it cost a red CI (carry-forward from Epics 5, 6, 7)
The Epic 6 retro's #1 action item ("stand up reliable integration-test infrastructure") was **not addressed**, for the third epic running. Direct, concrete consequence: the operator RLS matrix in `extraction-review-queue-operator.rls.test.ts` (authored in 8.1, its run *deferred* because there's no local supabase/testcontainer) **had never actually executed** until PR CI. On the first push it failed — the `OPERATOR DELETE affects ZERO rows` assertion expected a 0-row result, but the operator (the `authenticated` role, `REVOKE ALL` + `SELECT`/`UPDATE(3 cols)` grants only) is denied DELETE at the **GRANT layer** (42501) before RLS filtering. The test expectation was wrong; the production posture was correct (and stronger). One follow-up commit (`92b55eb`) fixed it. **This is the textbook cost of an unaddressed load-bearing action item** — a defect that an existing test *should* have caught locally instead surfaced in CI on a PR.

### Epic ACs encoded assumptions about the code that turned out wrong
Two Epic 9 stories hit spec-vs-reality gaps:
- **9.4:** the epic's stub-era signatures (`NOT_IMPLEMENTED`, `no_fixture`) are *error messages*, not the `uploads.metadata.reason` values actually stored (`retries_exhausted` etc., after pg-boss retry exhaustion). A literal reason-filter would have matched zero rows. The implementation reconciled to a `--before` timestamp as the reliable discriminator and documented the gap.
- **9.1:** AC6 anticipated lab/date extraction, but the first implementation left `collectedAtText` unset — the very gap that became the HIGH review finding (every field quarantined).

**Lesson:** ACs written before implementation can encode wrong assumptions about the existing code's real data shapes. Specs touching stored state should cite the *actual* column/value, verified against the code, not the aspirational name.

### Crossing an epic boundary on one branch made the PR heavy
Epic 9 was built on the Epic 8 worktree (Francis's explicit decision, since spinning a fresh worktree from a pinned background job wasn't possible). It worked, but it produced a 9-commit, two-epic PR and a two-epic retro. Acceptable here; worth flagging that epic boundaries are a natural merge point we skipped.

### Lockfile churn noise (recurring from Epic 6)
Adding the AWS SDK triggered a one-time ~14 KLOC YAML quote-style normalization of `pnpm-lock.yaml` (the committed lockfile predated pnpm@10.19.0's serialization). Pure noise in the diff; resolution intact. Recurs whenever a dep is added on a lockfile that drifted from the pinned pnpm.

### Sprint-status bookkeeping drift
Post-merge, `sprint-status.yaml` still shows `8-1`/`8-2` as `review` (they're merged/done) and has **no `epic-9-retrospective` key**. Minor, but the source-of-truth tracker is now slightly out of sync with reality.

## 5. Insights — name them

### Adversarial review's value scales with surface novelty
On a brand-new integration with no in-repo prior art (Textract), the AC-conformance layer is the *weakest* signal and the diff-only / repo-research layers are the strongest. Every Epic 9 HIGH came from a hunter reasoning about data flow or reading SDK source — not from checking ACs. **Budget the deepest review for the most novel surface**, and expect the Acceptance Auditor to pass clean while real bugs remain.

### "Pure core + thin shell" is now the house pattern for external integrations
Mapping, config-gate, error-classifier, re-enqueue-planner all followed it. It is the structural answer to "how do we unit-test an integration we can't call in CI" (NFR-S8). Codify it: any new external-service seam ships a pure logic module + a thin I/O shell, with the logic fixture/fake-env tested.

### "Deferred but authored" tests are a liability without infra to run them
8.1/8.2 authored RLS tests but couldn't run them locally, so a wrong assertion sat latent until PR CI. A test that never runs is worse than no test — it gives false confidence. Either the infra runs it, or the spec shouldn't claim it as covered.

### Presence-not-validity is the right altitude for boot gates (NFR-S8 corollary)
9.2's gate checks credentials are *configured*, not *valid* (a live STS probe would violate no-live-AWS-in-CI and couple boot to AWS uptime). This is the same constraint that drove the pure-mapping split — NFR-S8 shapes the whole epic's testability story.
