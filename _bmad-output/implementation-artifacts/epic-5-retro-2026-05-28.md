## 2. What Went Well

### Stacked-PR strategy held up across six stories

The Epic 4 retro endorsed the worktree+single-PR pattern for 4 stories. Epic 5 doubled it to 6 — and it **still scaled**. Concrete wins:

- Continuous review context: the reviewer for Story 5.6 could read 5.1–5.5's audit-kind catalog without flipping PRs.
- Zero cross-story merge conflicts on the shared `sharingRouter` (5.1, 5.2, 5.3, 5.4, 5.5 all touch it).
- Spec → feat → fix trio per story gave a recognisable git rhythm — `git log --oneline main..HEAD` reads like a changelog.
- Epic 6 inherits the branch (Story 6.1 already landed on top of 5.6 in the same worktree) — proves the pattern is composable across epic boundaries when the user's intent is "one logical product surface, one PR."

### Round-1 review caught two CRITICAL LGPD bugs in Story 5.6 _before_ merge

Story 5.6 R1 found two convergent CRITICALs that would have been LGPD-reportable in production:

1. The `account.deletion_failed` audit row used the raw `patientId` — re-leaking the re-identification key that step-2 had just spent its entire existence pseudonymizing.
2. Supabase Storage `list()` defaults to 100 items; long-time patients with >100 lab uploads would silently orphan everything past page 1 — direct LGPD Art. 18 violation.

Both were caught and patched (pseudonym uuid for the failed audit; paginated `limit:1000` + `offset` loop) before the story flipped to `review`. **This is the strongest argument so far for keeping adversarial R1 mandatory on LGPD-touching code.**

### Audit-log discipline matured into LGPD infrastructure

Epic 4 introduced the partial-unique-index + `writeAuditLogIfNew` pattern for `letter.queued`. Epic 5 leaned on it heavily and extended it correctly:

- 5.5 export and 5.6 deletion both use **partial unique indexes for in-flight dedup** (`exports_active_uq ... WHERE status IN ('queued','generating')`; `account_deletion_requests_active_uq ... WHERE status IN ('queued','processing')`), paired with narrow `23505` catches in the resolver. Concurrent double-tap is server-enforced — no client-side dedup theatre.
- 5.6 went further and made the 23505 catch **also accept `status='complete'`** — an idempotency win: a completed deletion _is_ the requested outcome, so racing to "already-deleted" returns success, not an error.
- Audit-log append-only invariant (NFR-S4) survived account deletion via **pseudonymization in place** (AR20 ADR): `actor_id`/`resource_id` UPDATEd to a deterministic uuid from `sha256(patient_id || ACCOUNT_DELETION_SALT)`, metadata regex-scrubbed. The forensic chain survives; the identifying link doesn't.

### Outbox pattern landed clean on first try (Story 5.2)

The `conversation_starter.generate` pg-boss enqueue inside the same Drizzle transaction as the `share_tokens` INSERT — using `INSERT INTO pgboss.job ... ON CONFLICT DO NOTHING` — is the canonical outbox pattern. Story 5.2's spec spelled it out and R1 didn't have to fix anything about the tx shape. **The Epic 4 SAVEPOINT discipline learning fed directly into 5.2's spec quality.**

### 6-identity RLS matrix discipline stuck

Story 5.1 R2 introduced the 6-identity RLS test matrix mandate (`correctPatient`, `wrongPatient`, `serviceRole`, `doctorWithActiveToken`, `doctorWithExpiredToken`, `doctorWithRevokedToken`) into CLAUDE.md after R2 found three tests claiming the full matrix but shipping only the patient subset. **Every subsequent sharing-table test in 5.2 and 5.3 honoured the full matrix.** No regressions on this dimension in 5.3-5.6 R1.

### LGPD Art. 18 surfaces correctly exempt from premium gating

Both 5.5 (data portability / export) and 5.6 (right-to-erasure / deletion) use `protectedProcedure`, NOT `premiumProcedure`. Gating LGPD rights on a paid tier would be illegal. Reviewers verified this on both stories and CLAUDE.md now codifies it in two separate appendix sections ("Export discipline" and "Account deletion discipline"). Future maintainers cannot accidentally premium-gate these surfaces without overriding documented intent.

### Deferred-server-write pattern (Story 5.4)

The 5 s undo on revoke is implemented as **deferred server write**: cancelled revokes never hit the DB, so there's no audit noise from confused-and-then-undone patients. This is the same trade-off Story 5.6 inherited at a longer (30 s) window for irreversible deletion. The pattern is now reusable for any patient-action-with-undo.

## 3. What Hurt

### Round-1 patch volume is structurally high — and not all of it should be there

70+ R1 patches across 6 stories is a lot. Some of that is the right answer (5.6's two CRITICAL LGPD bugs would never have been spotted at spec time). But some of it is recurring shapes that **should be caught at spec time, not R1**:

- **Idempotency of in-flight unique constraints** keeps showing up as an R1 finding (5.1 share_tokens 23505 + re-SELECT, 5.5 exports 23505, 5.6 deletion 23505). The pattern is now CLAUDE.md-codified twice — the next story spec that introduces a partial unique index should pre-write the 23505 catch.
- **Nullable column gotchas** (5.2 CRITICAL — `configureBiomarkers` SELECT FOR UPDATE silently rejected every `no_expiry` token because the predicate didn't handle NULL). Whenever a story makes an existing column nullable, every read path that uses that column in a predicate needs a spec-time audit.
- **Resolver-time vs worker-time clock divergence** (5.5 R1 fix — `record.exported.metadata.requestedAt` had to be re-sourced from `exports.requested_at` to be authoritative). This is a recurring shape across the epic.

Honest reading: the R1 cycle is _working_ (nothing CRITICAL/HIGH shipped), but the spec → dev handoff is leaking known bug patterns. **Next epic's create-story step should include a "known R1 gotcha checklist" derived from CLAUDE.md.**

### "Subagent API overload required manual patch application" (Story 5.6)

The 5.6 R1 fix-up had to be hand-applied because the subagent ran into API overload mid-patch. The work shipped, but the process glitch is worth noting — when the patch list is long (9 patches incl. 2 CRITICAL) and the agent fails partway, recovery is manual and error-prone. Future mitigation: stage R1 patches as ordered, idempotent commits so a partial-apply can resume cleanly.

### Migration deferred for the second epic in a row

Stories 3.5 and 4.4 each landed a consolidated migration after their respective epics' schema work. Epic 5 shipped 5 new tables via `pnpm db:push` and _no production migration_. This is the established pattern, but the queue is now: **5 dev-only tables waiting on one migration story before any of Epic 5 can deploy to prod**. The longer that queue, the higher the risk that `drizzle-kit push --force` and the eventual handwritten migration drift. Recommend a 5.7 / Epic-5-baseline migration story before opening Epic 6 to production deploy.

### Two stories declared "review" but PR #56 hasn't merged

All six Epic 5 stories show `review` in sprint-status. PR #56 is still open. That's fine for the retro (we're capturing the implementation journey), but it means **the retro's "shipped" claims are pre-merge** — the prod deploy gate is still ahead. If R2 review on the merged PR surfaces new findings, the retro will need an addendum (same pattern as Story 3.5's Epic 3 retro addendum).

### Story 5.5 PDF fonts deferred

Lora + DM Sans PDF font bundle was deferred; the export currently uses Helvetica fallback. The deferred-work entry is tracked, but it's a visible UX regression vs. the LetterReader's Lora rendering. A patient who exports their PDF and then opens their Letter side-by-side will notice the typographic inconsistency.

### pg-boss job-payload cleanup is best-effort

Story 5.6 step 4 DELETEs from `pgboss.job` + `pgboss.archive WHERE data->>'patientId' = $1` to prevent raw uuid leaking via queue payloads until archive sweep. This is **best-effort** — if the DELETE fails, the patient uuid persists in queue payloads until pg-boss's own archive policy reclaims it. Acceptable today (consumer logs rowCount on failure), but it's a forensic-cleanliness debt item that compounds if future epics add more queues handling patient data.

## 4. Themes & Lessons

### Lesson 1: Adversarial R1 is the LGPD safety net

Two CRITICAL LGPD bugs in 5.6 alone were caught only because R1 reviewers were instructed to assume malice. Cost: one extra review cycle per story. Benefit: zero LGPD-reportable bugs reached merge. **This is the single most valuable process gate the project has.** Do not regress.

### Lesson 2: Pseudonymization > Deletion for append-only invariants

The AR20 ADR (deterministic SHA-256 with rotated salt) is the right answer when an append-only audit log meets a right-to-erasure regulation. Salt rotation invalidates linkability _across the rotation boundary_ — a documented, acceptable trade-off. Future audit-touching erasure work should reuse this pattern verbatim, not reinvent it.

### Lesson 3: FK cascade audit is a permanent ongoing obligation

CLAUDE.md now mandates: every NEW FK to `users(id)` MUST have `onDelete: 'cascade'` or the deletion will leave orphan rows. `audit_log` is the deliberate exception (pseudonymize-only). `account_deletion_requests.patient_id` is intentionally FK-less (the ledger row outlives the user). This is not a one-time audit — it's a discipline every PR touching `users(id)` must honour, forever. The CLAUDE.md note is the enforcement mechanism. Reviewers must explicitly check this on every relevant PR.

### Lesson 4: Partial unique index + narrow 23505 catch is the in-flight dedup pattern

Used 3 times in this epic (5.1 share_tokens, 5.5 exports, 5.6 deletion). The shape is now mature:

- DB: `CREATE UNIQUE INDEX ... ON (key) WHERE status IN ('in_flight_states')`.
- App: optimistic INSERT, narrow `if (err.code === '23505') { /* return existing or success */ }` else `throw`.
- 5.6's twist: also treat `status='complete'` as success (the requested outcome already happened).

The next story that needs "single in-flight per key" semantics should reuse this pattern, not invent another lock-based scheme.

### Lesson 5: 6-identity RLS matrix is the new minimum for shared-data tables

5.1 R2's docstring-vs-implementation gap (claimed full matrix; shipped patient subset only) hardened into CLAUDE.md policy. The matrix discipline held through 5.2-5.6. The reviewer's job on a new shared-data table is now: _count the `it(...)` blocks, count the identities in the docstring, refuse review if they don't match._

### Lesson 6: LGPD rights are NOT premium features

Two appendix sections in CLAUDE.md (5.5 Export discipline, 5.6 Account deletion discipline) now explicitly state: `protectedProcedure`, never `premiumProcedure`. This is load-bearing legal text disguised as a tooling preference. Future reviewers and future Claudes must treat it as immutable.
