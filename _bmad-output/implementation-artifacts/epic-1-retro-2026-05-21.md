## What Went Well

### 1. The single-write-path pattern compounded across stories

Story 1.1's `writeAuditLog` set the precedent; Story 1.2 mirrored with `writeConsentGrant` / `writeConsentGrantIfAbsent`; Story 1.4 added `writeConsentRevocation`; Story 1.5 added `writeUpload`. By story 1.5 the pattern was so well-established that the dev notes referenced "Story 1.1 pattern" without needing to elaborate. New cross-cutting concerns (FR33 audit emit, ON CONFLICT idempotency, RLS-failure propagation) land in one place per table.

### 2. The `protectedProcedure` transaction wrap absorbed every atomicity question

Every story-1.4 and 1.5 code review surfaced the same shape of question — "does a failed audit roll back the prior write?" — and every time the answer was the same: yes, because `protectedProcedure` already wraps the resolver in `ctx.db.transaction`. The Story 1.4 code review (P27) even reached for a redundant inner transaction before the investigation showed it was unnecessary; the trade-off note from Story 0.4 paid back five times this epic.

### 3. The validators package became the canonical pt-BR copy + route home

Stories 1.2, 1.3, 1.4, 1.5 all added their constants to `packages/validators/src/index.ts` without exception. By Story 1.5 the file was ~570 lines but every screen on Expo + Web pulled strings from there. Zero duplication across platforms. The `isConsentScreenType` predicate extracted in Story 1.4 review (P31) became the template for Story 1.5's `isUploadMimeType`.

### 4. The adversarial code review caught real exploitable bugs

- Story 1.3 round 1: 5 High findings — three-fail counter resets on remount (AC3 broken), iOS lockout codes mis-classified, cold-launch lock race with deep-link callback, `signOut` throw strands the patient, lock screen acted as session bypass. Round 2 caught further regressions from round 1's fixes.
- Story 1.4 round 1: client-supplied `version`/`grantedAt` rendered as authoritative in detail screens, `router.replace` in render body, SQL policy not idempotent on re-apply.
- Story 1.5 round 1: client-controlled `storagePath` could forge DB rows (upload-bypass chain). Round 2 caught a runtime blocker — round-1's pg-boss column names were authored against v10 docs while the project pins v12.18.2 with snake_case columns. Tests passed because `db.execute` was mocked.

That last one is the headline of the epic. Without round 2, every `confirmImport` would have thrown `column "retrylimit" does not exist` at runtime. Mocked-execute tests masking real SQL errors is a known testing-strategy trade-off, but **the round-2 review caught it before merge**. That's review paying for itself.

### 5. F37 reconciliation in Story 1.4 was a clean architectural fix

Story 1.2 deferred F37: the partial unique index on `consent_grants` plus the "revocation = new row with revoked_at" pattern from architecture.md were incompatible — a revocation INSERT couldn't replace the existing active row, blocking re-grants. Story 1.4 resolved it with a narrow UPDATE-revokedAt RLS policy + defenses-in-depth trigger that hard-rejects updates to any other column (and, after round 2, rejects un-revoke transitions and bounds the timestamp to ±1 minute of `NOW()`). The append-only intent of `consent_grants` is now enforced at three layers (RLS USING, RLS WITH CHECK, trigger). Patient-initiated revoke + re-grant now works end to end.

### 6. The onboarding flow grew without rewrites

- Story 1.1 ends at `/onboarding/consent`.
- Story 1.2 ends at `INICIO_ROUTE`.
- Story 1.3 inserts biometric → import would have to come after; route constant trivially redirected. Story 1.2's `router.replace({ pathname })` object-form pattern made it a one-line change.
- Story 1.5 inserts import → again a one-line redirect target change in `biometric.tsx` (Expo) and `consent-flow.tsx` (web).

Each story added one screen between two others without touching downstream code. The route-constant discipline from Story 1.2's review (round-2 P30) was the seam.

## Challenges

### 1. The pg-boss v10/v12 docs trap (round-2 P48, story 1.5)

The round-1 fix for "row defaults disabled the queue's retry policy" was authored against pg-boss v10 docs. The project pins v12.18.2. v12 renamed the job-table columns to snake_case (`retry_limit, retry_delay, retry_backoff, dead_letter`) AND introduced table partitioning. A bare `INSERT (name, data)` worked in v10; in v12 you need the snake_case retry-policy columns AND a queue partition (created automatically by `boss.createQueue`).

The round-1 patch would have failed at runtime on every `confirmImport`. Unit tests passed because they mocked `db.execute`. The defect made it through:

- The dev who wrote it (didn't check the installed version's source).
- A round-1 review pass (didn't run the SQL against a real Postgres).
- A typecheck + lint + test pipeline (mocked the SQL path).

Round-2 review caught it. This is the strongest argument for the "round 2 always" pattern this epic established.

### 2. Mocked-execute tests are a Class-of-bug

Three different stories' tests asserted `tx.execute` was called the right number of times. None of them ran the SQL. This pattern works for asserting _that_ a side effect happened (audit insert, pg-boss enqueue, RLS SET LOCAL) but it doesn't catch _whether_ the SQL is valid. Story 1.5 round 2 was the wake-up call.

Integration tests against a local Supabase + pg-boss instance exist as a documented intent (the `rls-adversarial` CI job runs RLS tests against `supabase start`), but the application-layer SQL (the actual pg-boss enqueue, the consent grant insert with ON CONFLICT) doesn't have an integration-test seam yet.

### 3. The Expo `pickImages` dead-code path

The `useImportFiles` hook exports both `pickDocuments` (PDF + image via `expo-document-picker`) and `pickImages` (image via `expo-image-picker`). The onboarding screen only wires `pickDocuments`. The `expo-image-picker` dep, the `NSPhotoLibraryUsageDescription` Info.plist string, the plugin in `app.config.ts`, and the `PHOTO_LIBRARY_PERMISSION_PT_BR` constant all exist as scaffolding for a CTA that doesn't ship. F60 deferred. On iOS, photo-library uploads currently flow through the Files app, not the Photos library — an FR2 deviation that's documented as a deferred concern.

### 4. The signed-URL trust model needed two review rounds to nail down

The original Story 1.5 implementation:

- Trusted client-echoed `storagePath` in `confirmImport` (forgery vector).
- Never verified the storage object actually existed (could enqueue extraction jobs against nothing).
- Trusted client-claimed `sizeBytes` + `mimeType` for the audit log.
- The "storage RLS provides defense-in-depth on the signed PUT" comment was wrong — service-role-minted signed URLs don't carry the patient's `auth.uid()`, so RLS doesn't fire on the PUT.

Round 1 closed the storagePath forgery, the object-existence check, and a partial fix on the audit metadata. Round 2 finished the audit fix (hard-reject non-allowlisted content types instead of falling back to client claim), added the server-side size cap (Supabase Storage has no per-bucket limit configured), and corrected the trust-model comment. The trust model is now: signed URL secrecy + TTL on the PUT, server-derived path on every confirm, server-reported metadata on every audit row.

### 5. The native-rebuild requirement is documented but not enforced

Each Expo native-module addition (`expo-local-authentication`, `expo-document-picker`, `expo-image-picker`) requires a fresh Expo Dev Client build. The dev README doesn't yet have a "when you pull, run this" section. F48 deferred. Will hurt onboarding new devs to the project.

## Key Insights

1. **"Atomicity via outer transaction wrap" is now load-bearing across the codebase.** Every multi-write resolver depends on `protectedProcedure` opening a transaction. Story 1.4 P27 investigation made this an explicit, tested invariant — but the test exists only at the `consent.revoke` resolver level. If a future contributor changes `protectedProcedure` to a non-transactional pattern (e.g., for read-only routes), six resolvers silently lose their rollback guarantee. Write a checklist + maybe a test that catches the `ctx.db.transaction` wrap directly in `trpc.ts`.

2. **Mocked-execute tests need an integration backstop.** Story 1.5 round 2 caught a runtime-only bug that unit tests couldn't see. A `pnpm test:integration` job that runs the actual resolvers against `supabase start` + `pgboss` would have caught it pre-commit. Cost: meaningful CI time. Worth it for the upload contract Epic 2 is about to extend.

3. **The "two review rounds, always" pattern is paying for itself.** Round 1 catches the headline bugs the dev session missed; round 2 catches the regressions round 1 introduced. Story 1.3 needed THREE rounds before settling. The marginal cost (one extra LLM session per story) is dwarfed by the cost of shipping a runtime-broken `confirmImport`.

4. **Single-write-path + ON CONFLICT DO NOTHING + audit-on-real-insert is the canonical idempotency pattern.** Story 1.1 → 1.2 → 1.4 → 1.5 all use it. Future stories should never invent new idempotency patterns; reach for this one.

5. **Cross-version SDK assumptions need version-pinned source verification.** The pg-boss v10/v12 mismatch (P40 → P48) is the second time this epic that a stale doc-set tripped us — the first was Tamagui in Epic 0. For pg-boss specifically, the install pinning was easy to verify (`grep retry_limit node_modules/.pnpm/pg-boss@*/dist/plans.js`) — add this kind of source-grep to the per-story Dev Notes when raw SQL or low-level libs are involved.

6. **Storage RLS as defense-in-depth is a misconception for signed-URL uploads.** This was buried in the Story 1.5 Dev Notes from the start. The actual safety on the signed PUT comes from server-side path construction, URL secrecy, and URL TTL — NOT from RLS. The storage RLS still defends against direct anonymous-key reads of objects. Document this distinction more visibly in architecture.md when Story 2.x revisits storage.

7. **Deferred-work file is the epic's actual debt ledger.** Epic 0 added 44 items; Epic 1 added 48 more (F19–F66). Stories tag them with `[Review][Defer]` and they all flow to `deferred-work.md`. Auditing this file at Epic 2 start will surface what to address before Epic 2 vs. what truly belongs in Epic 5/8 ops. Recommendation: scheduled "F-item sweep" at the top of every epic — pick 3–5 items, fold into Epic prep work.

## Significant Discoveries Affecting Epic 2

### Discovery 1: Story 1.5 took ownership of the `uploads` schema from Story 2.1

The `uploads` table is now defined, has RLS policies, has a Supabase Storage bucket + RLS, has the `extraction.document` pg-boss queue, has the `requestImport` / `confirmImport` procedures, and has the `idempotency_key` UNIQUE constraint. Story 2.1's spec (per `epics.md`) reads: "patient uploads a PDF blood test result … `uploads` row is created with status `queued` and a unique `idempotency_key` … `ExtractionPulse` component appears." Most of that — schema, idempotency, queue contract — already exists.

**Impact on Epic 2.1:** scope shrinks substantially. Story 2.1 should now be: "wire the post-onboarding upload UX onto the existing `uploads` schema + queue contract; introduce the `ExtractionPulse` UI component; add `source = 'post_onboarding'` writer path." Story 2.3 (extraction worker) gets the heavy lifting — it consumes the `extraction.document` queue rows Story 1.5 has been producing since deploy.

**Action:** Review Epic 2 stories before starting and re-scope 2.1 and 2.2 (FR2 — image upload) against what's already shipped. The `uploads.confirmImport` procedure already accepts all four allowed mime types; 2.2's incremental scope is the photo/camera-roll picker UX.

### Discovery 2: The pg-boss client is NOT a dep of the API server

The API enqueues via raw SQL into `pgboss.job` to avoid pulling pg-boss into the request-scoped Drizzle connection pool. This is documented in Story 1.5 Dev Notes. Story 2.3 (extraction worker) will read those jobs and dispatch them. Story 2.5 (upload status + push notifications) needs to read job state — and the same raw-SQL coupling decision applies.

**Impact on Epic 2:** Story 2.5's "view upload status" tRPC procedure can read from `uploads.status` directly (it's the application-domain truth) instead of from `pgboss.job`. The pg-boss state is for the worker's retry / dead-letter contract, not for patient-visible status.

### Discovery 3: Storage RLS doesn't fire on signed-URL PUTs

Documented above. Epic 2's Story 2.1/2.2 will create more signed URLs for post-onboarding uploads. The trust model stays the same: server-side path construction + URL secrecy + TTL. Don't waste review cycles on "but RLS protects the PUT" in Epic 2.

### Discovery 4: Storage bucket size limit is unset

Story 1.5 round-2 P51 added a server-side `sizeBytes` cap of 5 MB. Supabase Storage has no per-bucket maximum configured. Setting one (e.g., 10 MB to give server-side validation headroom) would be a belt-and-suspenders fix. Worth doing once Epic 2 is in flight.
