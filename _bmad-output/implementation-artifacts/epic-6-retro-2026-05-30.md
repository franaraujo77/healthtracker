## 3. What Went Well — concrete examples

### Stacked-story-on-stacked-story PR worked again, at increased scope

PR #57 stacked **5 stories** (6.2–6.6) on top of PR #56 (Epic 5 + Story 6.1). The pattern Epic 5 retro endorsed continued to scale — each story landed as a `feat`/`fix` commit + standalone R1 review file, so the reviewer for Story 6.6 (migrations) could walk the prior 5 stories' audit-kind catalog and RLS-policy choices without flipping PRs. Zero cross-story merge conflicts on the shared `sharingRouter` even though 6.2/6.3/6.4/6.5 all touched it. Stacking across epic boundaries (Epic 5 → Epic 6) survived two retros now; the pattern is composable when "one product surface, one PR" is the user intent.

### `professionalSessionProcedure` middleware emerged as a new reusable pattern

Story 6.5 originally placed activation gates (`SELECT FROM professionals`) inside resolver bodies. Story 6.5 R1 MEDIUM-1 caught the procedure-name lie ("professional session" implied session+activated, but only verified session) and the R1-followup folded the activation SELECT **into the middleware** (`packages/api/src/trpc.ts:129-202`). New test file `professional-session-gate.test.ts` mirrors `doctor-procedure-session-gate.test.ts` — both gate tests now lock the contract. This is a clean architectural lesson: **procedure-name truthfulness is a load-bearing invariant.** A consumer of `professionalSessionProcedure` is now guaranteed both gates without inline duplication.

### The `supabase/migrations-postapply/` directory + GHA `psql` autocommit step is a permanent platform contract

Story 6.6 R1 H1 caught that `0006_*_active_uq.sql` used `CREATE UNIQUE INDEX CONCURRENTLY` inside Supabase CLI's implicit per-file tx (SQLSTATE 25001). The R1 followup created `.github/workflows/supabase-deploy.yml`'s post-apply `psql -v ON_ERROR_STOP=1 -f` loop and moved the file. **This is now the official pattern for any CONCURRENTLY DDL across all future epics.** Both Epic 5 baseline (`0008_epic_5_partial_uniques.sql`) and Epic 6 (`0007_epic_6_patient_invites_active_uq.sql`) landed under the new contract, and CLAUDE.md carries the ops note. Future epics (7, 8) inherit it for free.

### Prior-story learnings landed correctly

- **Story 5.6 deferred-server-write pattern** (5 s undo) reused conceptually in Story 6.3's per-session banner dismiss (in-memory, no DB churn for ephemeral state).
- **Story 5.1's `share_token_biomarkers` composite-PK pattern** reused in Story 6.5's `staleness_thresholds` (after R1 M3 corrected the dev's `uniqueIndex`-instead-of-`primaryKey` slip).
- **Story 5.5's `requestExport` `onConflictDoNothing` + post-conflict SELECT** reused in Story 6.3's `activateProfessionalAccount` and Story 6.4's `createPatientInvite`. Partial-unique-index discipline (5.1/5.5/5.6 lineage) honoured in `patient_invites_professional_identifier_active_uq` WHERE `status = 'pending'`.
- **6-identity RLS matrix** (Epic 5 institution) extended to **7-identity** in Story 6.4 (`UNRELATED_DOCTOR` row added) — and held across `professionals.rls.test.ts`, `patient_invites.rls.test.ts`, `staleness_thresholds.rls.test.ts`. Every new shared-data table in Epic 6 honoured the full identity grid.
- **Story 5.6 FK-cascade-vs-set-null discipline**: Epic 6 introduced TWO new `ON DELETE SET NULL` FKs to `users(id)` (`pending_invites.resolved_user_id`, `patient_invites.resolved_user_id`). Both are documented exceptions in CLAUDE.md alongside the original `account_deletion_requests` ledger case. Reviewers held the line — every other FK in Epic 6 uses `cascade`.

### R1 reviews caught material defects, including one WCAG AA compliance bug

- **Story 6.2 R1 HIGH-3**: open-redirect / token-tag confusion on `/m/[token]/auth/callback` — `searchParams.shareTokenId` not cross-checked against `[token]` route segment. Patched.
- **Story 6.3 R1 HIGH-1**: post-activation banner stayed visible after success (RSC-vs-client cache invalidation mismatch — `invalidateQueries` invalidated a key nothing read). Patched.
- **Story 6.5 R1 HIGH-1**: BiomarkerCard stale chip used `backgroundColor="$textSecondary"` (a text token) yielding ~2.3:1 contrast on dark theme — **WCAG AA fail**. Patched by swapping to `$accessLogNeutral`. Best evidence that adversarial R1 catches not just security/correctness but also accessibility regressions that visual review can miss.
- **Story 6.4 R1 HIGH-1**: integration test coverage gap on `createPatientInvite` (3 of 6 spec cases shipped). Surfaced as HIGH for visibility; flagged rather than fully closed because the resolver's narrow 23505 catch + activation gate are still locked by unit tests.

Five HIGH findings caught and resolved before merge; zero CRITICAL findings. The R1 cycle continues to earn its keep.

## 4. What Hurt — recurring patterns

### Integration test infrastructure is dead in this worktree

Stories **6.4, 6.5, 6.6** all SKIPPED `test:integration` with the same rationale: "Rancher Desktop's lima VM rejects testcontainers' docker.sock bind-mount." This is **3 stories in a row** running on degraded coverage. The RLS suites that lock the invariants for `professionals` / `patient_invites` / `staleness_thresholds` exist on disk but never executed in this epic. Production safety today rests on (a) unit tests around resolvers, (b) prior epics' integration suites that ran when Docker was up, (c) the `rls-adversarial` GHA job that runs on a clean shadow DB. The local development feedback loop is degraded.

This is a **meta-problem**. The fix is platform-level: either swap Rancher for Docker Desktop, wire testcontainers to a remote Docker host, or maintain a one-command local Postgres fixture that bypasses testcontainers entirely. Action-item below.

### Migration prerequisite (linked Supabase project) was an invisible gate that surprised everyone

Story 6.6 spec instructed: "run `supabase db diff --use-migra --linked -f epic_6_doctor_accounts` against the linked project." The dev correctly stopped when the shadow-DB apply of 0005 failed because `pending_invites` (an Epic 5 table) had never been migration-authored — only `pnpm db:push`'d. The pre-existing **Epic 5 migration gap** was caught only because Story 6.6's apply chain hit it. Worse: this exact issue was an Epic 5 retro action item (item 1: "Author Epic-5 consolidated Supabase migration"). It was deferred and **only surfaced when PR #57's `rls-adversarial` CI check went red** — i.e., the safety net worked, but the action item was carried unaddressed for an entire epic.

The R1-followup-2 on Story 6.6 inlined the entire Epic 5 baseline (`0005_epic_5_sharing_baseline.sql`, ~485 lines: 4 enums, 6 tables, 6 RLS policy bodies, Storage bucket, `pseudonymize_patient_id()` helper) and reordered the Epic 6 files (`0005` → `0006`, `0006` → `0007`). This worked but burned an extra full review cycle. **Lesson: action items carrying load-bearing CI gates must be tracked as blockers, not as next-epic notes.**

### Spec-file corruption during editing (Story 6.5 sed regression)

Story 6.5's spec file landed with ACs 1–13 truncated to one-liners due to a sed regression in the dev's editing tool. The R1 review caught this as MEDIUM-2 — load-bearing contracts (no-DELETE-policy rationale, `biomarkerStaleness` parallel array shape) could not be reviewed from the spec text alone. The R1 followup restored the canonical Given/When/Then blocks verbatim from `epics.md` lines 1521–1545. **Lesson: editing tools that operate on long markdown files need a roundtrip diff check; sed-style operations on epic-output specs are a bug class, not a one-off.** Prefer line-anchored edits with explicit context windows.

### Supabase IPv6 deploy issue forced an ops mitigation

The new `psql -f` post-apply step in `supabase-deploy.yml` hit GHA's IPv6-only resolution of `db.<ref>.supabase.co` and required swapping to the Supavisor session pooler URI via a new `SUPABASE_DB_URL` GHA secret. This is a **non-obvious production deploy gate** that future deploy-touching stories must remember. Ops note added in CLAUDE.md but it's the kind of trap that bites again whenever a new psql-based workflow step is introduced.

### Activation-gate placement overstatement (architectural smell)

Story 6.5 originally claimed `professionalSessionProcedure` guaranteed "activated doctor," but the middleware only verified session existence. R1 MEDIUM-1 caught it. The followup moved the gate INTO the middleware. **Pattern lesson**: when a procedure name encodes a guarantee (`doctorProcedure`, `professionalSessionProcedure`, `premiumProcedure`), the middleware MUST enforce that guarantee end-to-end. The resolver body cannot be the first line of defence for a name-encoded invariant. Future story specs should explicitly state where each gate lives, in the procedure-middleware section.

### Stacked-story PR review burden

PR #57 shipped 5 stories across ~3,000 LOC of net diff (excluding lockfile). That is a lot for one human reviewer to walk. The mitigation is structural — per-story R1 review files give the reviewer a per-story narrative — but the question is honest: would the next epic benefit from earlier merge points? Discussed in §6 below; the current evidence is that stacking still wins for tightly-coupled product surfaces like the doctor loop, but PRs covering 5+ stories should keep R1 reviews mandatory and dated per commit so reviewers can resume after interruption.

### Subagent API overload (recurring from Epic 5)

Epic 5 retro flagged "subagent API overload required manual patch application" on Story 5.6. Epic 6 had similar friction (multiple R1-followup commits per story, often hand-staged). No new mitigation shipped. Stays on the action list.

## 5. Insights — name them

### The 5-stacked-story-on-one-PR pattern works because each story carries its own commit + R1 review chain

The risk of stacking isn't the diff size — it's lost reviewability. PR #57 mitigated this by maintaining per-story R1 review files (`6-2-...-code-review-r1.md` through `6-6-...-code-review-r1.md`) and per-story `feat`/`fix` commit pairs. A reviewer can step through `git log --oneline` and read the matching R1 doc to understand each story in isolation. As long as the R1 discipline holds, the stacking pattern scales. Recommendation: **keep stacking for Epic 7 (4 stories, patient-side surface) and re-evaluate if Epic 8 wants tighter merge points.**

### Hand-authored migrations are defensible only when Drizzle is the source of truth

Story 6.6's `supabase db diff` path was blocked by the Epic 5 gap. The dev hand-authored 0005/0006 from the Drizzle schema + RLS policy source-of-truth files (verbatim copies of `packages/db/policies/custom_rls_*.sql`). The R1 reviewer verified RLS policy bodies byte-equivalent. **This validates the pattern**: when `supabase db diff` is unavailable, hand-authoring is acceptable _iff_ every object is verifiable against an existing source-of-truth artifact (Drizzle schema for tables/indexes/enums; policy files for RLS). Future migrations should follow this contract explicitly; CLAUDE.md should codify it.

### The post-apply migrations directory is now a first-class platform pattern

`supabase/migrations-postapply/` is the platform's answer to "DDL that cannot be wrapped in a tx" (today: CONCURRENTLY indexes; tomorrow: anything else CLI-tx-hostile). The contract is: bare DDL files, `IF NOT EXISTS` guards, lex-ordered psql apply via GHA after `supabase db push`. Document it as permanent in CLAUDE.md (already done).

### `rls-adversarial` as a fresh-DB migration apply gate

The Epic 5 baseline gap was caught by `rls-adversarial`'s clean-shadow-DB apply, not by code review. This is the highest-leverage CI job in the repo and its scope is broader than just RLS — it's the _only_ job that proves the migration chain is intact end-to-end. No action needed (it already exists and worked); just note that it earned its keep this epic.

## 7. Next-Epic Readiness — Epic 7

Epic 7 is "Patient Adds Personal Context to Their Record" — patient-side life events on Fingerprint timeline (7.1), pre/post emotional check-ins (7.2/7.3 Growth), voice memo at upload (7.4 Vision), incremental migration (7.5). The surface is **orthogonal to Epic 6** (patient-side, no doctor interaction; explicit `privacy_flag = 'patient_only'` on every Epic 7 table — never shared with doctor views).

### Dependencies on Epic 6

**Effectively none.** Epic 7's surfaces (`life_events`, `emotional_checkins`, voice memo on `uploads`) do not touch `share_tokens`, `professionals`, `patient_invites`, or `staleness_thresholds`. The only conceptual link is the explicit doctor-view privacy invariant, which Epic 7 specs encode as a RLS predicate (rows with `privacy_flag = 'patient_only'` MUST NOT appear in doctor RLS scope). The existing `app.current_share_token_id` doctor-RLS principal does not grant access to any Epic 7 table by default — a defensive RLS policy on each new table is sufficient.

### Deferred work that could block Epic 7

- **Epic 5 baseline migration** — already resolved in-epic (Story 6.6 R1-followup-2). No longer blocks.
- **Integration test infra** — the same Rancher/testcontainers gap will hit Epic 7's RLS suites. Should be addressed before Epic 7 stories author new RLS files, or Epic 7 will skip integration too.
- **`record_access` notification kind** (F167 from Story 2.8 deferred-work) — toggle ships forward-compat; emitter was planned for Story 5.3. Verify whether it landed; if not, Epic 7 doesn't need it but it's surfacing in `notification_preferences` consumers.
- **Lora/DM Sans PDF font bundle** (Story 5.5 deferred) — not an Epic 7 dependency.

### New tech / knowledge gaps for Epic 7

- **Audio recording** (Story 7.4 Vision): `expo-av` or `expo-audio` (SDK 54+ may have migrated). Web recording is out (mobile-first per UX-DR4). 30s cap + microphone permission flow + Storage bucket for audio blobs are net-new. **Decision needed**: a new private Supabase Storage bucket `voice_memos` (similar to `exports`) with patient-scoped RLS.
- **Calendar/date-picker UX** for retroactive life event dates (Story 7.1). Existing patterns: Story 2.7's `collectedAt` pattern (BIA submission) likely reusable.
- **Timeline marker rendering on FingerprintChart** (Story 7.1). Victory Native v41 was wired in Story 3.3 — extending it to render life-event markers is incremental, not net-new.

### Significant Discoveries

**None that change Epic 7's plan.** The doctor surface and patient personal-context surface are clean planes of separation. The only architectural ripple is that `BiomarkerCard`'s prop surface grew (`isStale`, `stalenessThresholdDays`, `state` already had `notable`/`watching`) — Epic 7's "life event marker on Fingerprint" may want a similar additive surface on `FingerprintChart`. Worth flagging at story-creation time but not a redesign.
