## What Went Well

### 1. The round-1 + round-2 review pattern is now a non-negotiable

Epic 1 closed with "round 2 always" as a recommendation born from Story 1.5 R2-P48 (the pg-boss v10/v12 docs trap). Epic 2 ran it as a hard process gate on every story. The data:

- **Story 2.3 R2** found 3 HIGH crash-recovery / transaction-boundary bugs that R1 introduced: terminal `applyUploadTransition` outside the `sql.begin()` block; `currentStatus()` mishandling `pending_review`; idempotent retry of an already-complete upload dead-lettering it.
- **Story 2.4 R2** caught R1's dead-code cross-upload guard (`existing.uploadId !== reviewRow.uploadId` was unreachable because the SELECT already filtered by upload_id), and a TZ-drift risk on the ON-CONFLICT re-SELECT probe.
- **Story 2.5 R2-P172** found the most consequential: R1-P152's `SELECT EXISTS … audit_log` then INSERT was a TOCTOU race under READ COMMITTED. Two concurrent dead-letter callbacks would both insert. Fix: partial unique index on `audit_log(resource_id, event) WHERE event IN (...)` enforced at the DB.
- **Story 2.7 R2-P211** found that R1-P201's `where: source <> 'manual_bia'` on `onConflictDoNothing` meant manual BIA conflicts couldn't no-op — they raised `unique_violation` (23505) as 500s. The duplicate-detection contract was silently broken.

Without round 2, four of these would have shipped. The pattern is the moat. Lock it in for Epic 3.

### 2. Single sanctioned write paths kept multiplying — and the discipline held

`writeObservation` (2.3), `writeReviewQueueEntry` (2.3), `writeBiaObservations` (2.7), `writePushToken` (2.5), `revokePushTokenByDevice` (2.5), `writeNotificationPreferences` (2.8), `getNotificationPreferences` (2.8), `enqueueNotificationSend` (2.5). Every cross-cutting concern landed in one place per table. By Story 2.7, `writeBiaObservations` fanned out to 3 × `writeObservation` calls + 1 × `writeAuditLog` inside the protectedProcedure transaction — patient action = one audit row carrying `observationIds: [3]` in metadata — and this required zero discussion because the pattern was established.

### 3. The worker/API SQL deviation got tooled, not refactored

Story 2.3 R1-P94 spec'd that the worker should import the API helpers; the worker's `postgres` driver vs API's `@vercel/postgres` Drizzle binding made that impractical. Rather than force a refactor mid-story, the spec was amended to acknowledge the deviation + ship a `UPLOAD_TRANSITIONS` snapshot-sync test (R1-P110) that pins the worker's arc map against the API's. Pragmatic shipping discipline. The full SQL-body drift detection stayed deferred (F103 / F112).

### 4. Validators-as-shared-truth scaled cleanly

Story 2.4 lifted `parseBrazilianDecimal` + `parseCollectedAt` from `services/extraction/src/normalize/` to `packages/validators/src/`, with the worker keeping local copies (eslint type-resolution under NodeNext was finicky). Story 2.5 added `failureReasonLabel`, `postOnboardingImportRoute`, and the `HISTORICO_*_PT_BR` family. Story 2.7 added `BiaSubmissionSchema` + 17 pt-BR copy constants. Story 2.8 added `NotificationPreferencesSchema` + `NOTIFICATION_KIND_TO_PREFERENCE` as the documented source-of-truth (2.8 R2-P229). By epic end, `packages/validators/src/index.ts` is ~880 lines but every screen pulls from it, and the kind→preference map is unit-tested for snapshot-sync between validators and the worker switch.

### 5. The state machine spine survived the patient-confirm path

Story 2.1 shipped `applyUploadTransition` + `applyDeadLetter` with the legal arc map. Story 2.3 was the first worker caller. Story 2.4's `confirmReviewFieldAsPatient` was the first patient-side caller and the trickiest — patient action → write observation → mark review row resolved → re-count remaining → maybe transition `pending_review → complete` → maybe emit `notification.upload_complete` audit + enqueue. The whole sequence runs inside the existing `protectedProcedure` transaction wrap (Epic 1's compounding pattern paying back yet again). Story 2.4 R2-P113 even moved the terminal `applyUploadTransition` *inside* the dispatch + audit `sql.begin()` block to close a crash-recovery gap. The spine held.

### 6. F-item discipline as a release valve

Epic 2 added 110 F-items (F67 → F176). The pattern of "patch what we can, document what we can't" kept stories shippable without quality drift. Examples:

- F123 — RLS adversarial test for `extraction_review_queue` (deferred to local Supabase availability).
- F135 — Expo client hook for `expo-notifications` (deferred because EAS Build is required; the tRPC mutation surface ships, the OS-level wire-up ships next).
- F141 — Lab-name aggregate column on `uploads` (the n+1-ish subquery in the push dispatcher is fine for now).
- F167 — `record_access` notification kind end-to-end (forward-compat scaffolding waiting on Story 5.3's doctor-views-record audit).
- F172 — 300ms toggle debounce (cosmetic UX flicker; ship without and revisit).

Every F-item has a one-liner + a story handoff. No "we'll fix it later, trust me."

### 7. The notification dispatcher's three-layer dedup landed clean

Story 2.5's `notification.send` pg-boss job uses `singleton_key = ${uploadId}.${kind}` (one push per upload-event). Story 2.5 R2-P172 added the partial unique index on `audit_log(resource_id, event)`. Story 2.8's worker preference gate adds a third layer (skip if `results_ready=false`). The same upload reaching `complete` via the worker direct-publish path AND via Story 2.4's patient-confirm path is now provably dedup'd at the DB layer, the queue layer, and the dispatch layer.

## Challenges

### 1. Round-1 patches kept introducing round-2 bugs in predictable shapes

Pattern across the epic:

- 2.3 R1 → 2.3 R2: terminal-state ack-skip swallowed crash-recovery; idempotent retry dead-lettered an already-complete upload.
- 2.4 R1 → 2.4 R2: P137's upload-id guard was dead code (P130 made it unreachable); P135's `hasOperatorOnlyRows` heuristic mis-triggered during the post-processing transient.
- 2.5 R1 → 2.5 R2: `?source=` query param never consumed (R1 added the route helper, no consumer); the SELECT-then-INSERT audit dedup was a TOCTOU race.
- 2.6 R1 → 2.6 R2: `enqueue`/`dequeue`/`recordAttempt` had no mutex; concurrent picks last-writer-wins on AsyncStorage.
- 2.7 R1 → 2.7 R2: ON-CONFLICT clause excluded manual_bia rows; the partial-index conflict became an unhandled `unique_violation`.
- 2.8 R1 → 2.8 R2: the fail-open catch swallowed programmer errors (TypeError, ReferenceError, SyntaxError).

The class of bug is "the round-1 patch was correct in isolation but wrong when composed with the surrounding system." Two takeaways: round-2 reviews must explicitly hunt for "what did round-1 break or leave half-finished" (already in the prompt template — keep emphasising it) and the fail-open / catch-all idiom is a repeated offender — narrow catches by default.

### 2. Mocked-execute tests bit us again, less severely

Story 1.5 R2-P48's lesson — mocked-execute tests don't catch runtime SQL errors — recurred in Epic 2 in milder forms. Story 2.3 deferred the SQL drift between worker and API as F112; Story 2.5's notification-emit raw SQL was hand-synced with the API helper with a comment pointing to F128. Story 2.7's `pnpm db:push` for the partial-index WHERE rewrite was flagged in R2-P213 as not-prod-safe but documented inline. We didn't get bit by a runtime SQL error this epic, but the testing-strategy gap remains. Real integration tests (Drizzle + Postgres testcontainer) are the right answer; F-items F112, F128, F134 all track variants of this.

### 3. The Expo client hook for push notifications is the longest-lived deferral

F135 spans Stories 2.5, 2.6 (sort of — different hook), and 2.8. The pattern is: ship the API surface, defer the native wire-up. Three stories cite it. The cost: AC4 of Story 2.5 (push delivery on completion) is operationally unverifiable today; AC1 of Story 2.8 (toggle changes affect delivery) requires that the underlying delivery actually works to test end-to-end. The toggles persist and the worker gate is unit-tested, but the loop isn't closed in a real device until F135 ships. **This is the single highest-priority defer.**

### 4. The R2-P171 query-param consumption pattern repeated twice

Story 2.5 R1-P153 added `postOnboardingImportRoute(source)` returning `/inicio?source=...` — and shipped without a consumer on either Início page. Round-2 R2-P171 wired it. Then Story 2.7 R1-P204 added the web "Adicionar medição" inline anchor link that DOES land on a real route — fine — but the muscle memory could have repeated. The pattern (add a URL with query params + assume the destination reads them) has a hidden expectation. Round-1 reviewers should check that *if* a query-string flag is added, the destination route consumes it. Adding to action items.

### 5. The kind → preference mapping was duplicated until R2-P229

Story 2.8 added the worker switch (`isPreferenceMuted`) AND R2 added a validators-side `NOTIFICATION_KIND_TO_PREFERENCE` map. The snapshot-sync test pins them, but the architectural ideal is one definition. We accepted the duplication because the worker uses snake_case columns and the API uses camelCase, and the cost of a shared adapter wasn't paying off this story. F-item-worthy if Epic 4's letter notifications add new kinds.

### 6. `pnpm db:push` is not a deployment strategy for partial-index WHERE changes (Story 2.7 R2-P213)

R2-P213 flagged that altering the WHERE clause on a partial unique index via `pnpm db:push` issues `DROP INDEX` + `CREATE UNIQUE INDEX` (non-`CONCURRENTLY`), taking a `ShareLock` and creating a window for a concurrent insert to violate the new constraint. The story doc has the inline ops note. For Epic 3+ schema changes that alter index WHERE clauses, we need a proper migration file, not push. F-item-tracked but worth flipping the default if it happens again.

## Next Epic Preview — Epic 3: Patient Can See Their Health Fingerprint Over Time

Four stories planned:

- **3.1** Patient views their complete longitudinal biomarker record.
- **3.2** Patient views the Fingerprint at Draw 1 with baseline-building context.
- **3.3** Patient views the Fingerprint at Draw 2+ with personal baseline band.
- **3.4** Patient views cached Fingerprint data while offline.

### Dependencies on Epic 2

- **`observations` schema** — Epic 3 is the first read-heavy consumer. The partial unique indexes from 2.7 (`source='manual_bia'` split) need verifying under a read path. The `deleted_at IS NULL` filter that 2.7 added MUST be applied by every Epic-3 query (F-item F-not-yet-numbered).
- **`(patient_id, collected_at desc)` index** — already shipped in Story 2.3; Epic 3 will be the first user.
- **`source` discriminator** — Fingerprint needs to distinguish `'extracted'` vs `'manual_bia'` vs `'patient_corrected'` rows visually.
- **`extraction_review_queue` resolved-state semantics** — Story 2.4 added the patient-confirm flow; Epic 3 must not surface unresolved review-queue rows in the Fingerprint (those aren't published observations yet).
- **Audit log volume** — Epic 2 added 6 new event kinds. Epic 3's read paths emit `observation.read` (Story 5.3-family pattern). Verify the audit table doesn't need an index on `(actor_id, event, created_at)` for the access-log query (Story 5.3) before that becomes a hot path.

### Preparation gaps identified

- **Testcontainer-based integration tests.** Five Epic-2 F-items (F103, F112, F128, F134, F140, F166) all reduce to "we need a real Postgres in CI." Epic 3's baseline-band math will be read-heavy SQL; mocking won't catch query plan issues. **Recommend: 1 prep day to set up `@testcontainers/postgresql` + a single seed-and-query test before Story 3.1 starts.**
- **Fingerprint query design.** Story 3.1's "longitudinal biomarker record" is a SELECT across `observations` filtered to the patient + `deleted_at IS NULL` + grouped by LOINC. The architecture doc has this sketched but not benchmarked. A 5-year-old patient with 50 BIA submissions + 20 extracted uploads × ~15 biomarkers each = ~1000 rows. Trivial. Don't over-engineer.
- **Baseline-band statistics.** Stories 3.2 / 3.3 need running mean + stddev per biomarker per patient. SQL window functions (PG ≥ 11) handle this fine; no client-side math needed.
- **F135 (Expo client hook) is still blocking AC2/3/4 verification on Story 2.5.** Doesn't block Epic 3 directly, but does block the end-to-end happy path for any patient who completes a Fingerprint upload via the offline queue. Recommend: schedule F135 as the first follow-up story of Epic 3 if there's a free slot.

### Technical prerequisites

- **Drizzle query patterns for partial unique indexes** — Story 2.7 R1-P201 (the `where` clause on `onConflictDoNothing`) and 2.7 R2-P211 (catching 23505 unique violations at the helper layer) are now templated. Epic 3 reads won't hit ON CONFLICT but the patterns are documented for future writes.
- **Drizzle `sql<T>` for jsonb extracts** — Story 2.5 `listUploadsForPatient` already uses `sql<string | null>\`${Uploads.metadata}->>'reason'\``; Epic 3 may need similar for any future per-observation metadata.
